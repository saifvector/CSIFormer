## 1. Executive Summary

Phase 46 resolves the critical blockers identified in Phase 45 by fully realigning the ESP32-S3 firmware's Wi-Fi channel and flash geometry with verified physical hardware and executing a clean, reproducible firmware rebuild under ESP-IDF / PlatformIO Core.

In Phase 45, an exhaustive audit uncovered two critical blocking issues:
1. **Wi-Fi Operating Channel Conflict:** Firmware hardcoded Channel 6 (2.437 GHz), whereas the physical laboratory AP (`Tp link`, BSSID `98:ba:5f:ef:28:26`) operates on Channel 7 (2.442 GHz).
2. **Three-Way Flash Size Discrepancy:** Physical hardware on `COM5` possesses 16 MB flash, but the binary image header contained an 8 MB setting, and the ESP-IDF build system generated flasher arguments specifying 2 MB.

Through empirical non-destructive inspection of the running hardware on `COM5`, both blockers were definitively characterized without guessing. The firmware source and build flags were systematically aligned to **Channel 7**, the flash geometry across PlatformIO and ESP-IDF was unified to **16 MB**, and a clean rebuild was successfully executed. All generated binaries (`bootloader.bin`, `partitions.bin`, `firmware.bin`, and `firmware.elf`) were verified for header alignment, partition fit, and checksum validity.

**Final Readiness Decision:** **`BUILD VALIDATED — AWAITING SEPARATE FLASH AUTHORIZATION`**.  
Zero physical firmware writes were performed during this phase.

## 3. Gate B — Flash Configuration Reconciliation

### 3.1 Flash Size Unification Matrix
The 3-way discrepancy discovered in Phase 45 was completely resolved by declaring 16 MB across all build layers:

| Layer | Phase 45 (Discrepant) | Phase 46 (Realigned) | Mechanism / Configuration File |
| :--- | :--- | :--- | :--- |
| **Physical Hardware Flash** | 16 MB (`0x7118`) | **16 MB** (`0x7118`) | Verified via JEDEC ID on `COM5` |
| **PlatformIO Board Config** | 8 MB (default board) | **16 MB** | `board_upload.flash_size = 16MB`, `maximum_size = 16777216` in `platformio.ini` |
| **ESP-IDF Kconfig (`sdkconfig`)** | `CONFIG_ESPTOOLPY_FLASHSIZE_2MB=y` | **`CONFIG_ESPTOOLPY_FLASHSIZE_16MB=y`** | Declared in `sdkconfig.defaults` & applied to `sdkconfig.esp32-s3-devkitc-1` |
| **Image Header (Byte 3 High Nibble)** | `0x30` (8 MB) | **`0x40` (16 MB)** | Generated by `esptool` image builder |
| **Generated `flasher_args.json`** | `--flash-size 2MB` | **`--flash-size 16MB`** | Emitted by ESP-IDF CMake / PlatformIO |
| **Generated `flash_args`** | `--flash-size 2MB` | **`--flash-size 16MB`** | Emitted by ESP-IDF CMake / PlatformIO |

### 3.2 Partition Layout Decision & Validation
The existing 2 MiB partition layout defined in [`firmware/esp32s3_csi_collector/partitions.csv`](file:///c:/Users/saifu/Desktop/4-1%20project/firmware/esp32s3_csi_collector/partitions.csv) was retained:

```csv
# Name,   Type, SubType, Offset,  Size,     Flags
nvs,      data, nvs,     0x9000,  0x6000,
phy_init, data, phy,     0xf000,  0x1000,
factory,  app,  factory, 0x10000, 0x1F0000,
```

#### Rationale for Retaining 2 MiB Layout on a 16 MiB Flash Module:
1. **Application Requirements:** The compiled CSI collector application is 654,848 bytes (0.62 MB). The factory partition provides 2,031,616 bytes (1.9375 MB), yielding **67.77% (1.31 MB) headroom**.
2. **Safety & Flash Geometry:** In ESP-IDF, the SPI flash MMU only maps the defined partition boundaries (`0x000000` to `0x200000`). The upper 14 MiB (`0x200000` to `0x1000000`) remains untouched, unpartitioned, and safe from unintended wear or overwrite.
3. **No OTA Required:** The node operates as a dedicated hardware sensor node without multi-partition OTA ping-pong requirements.
4. **Header Alignment:** Because the binary header and flasher arguments now declare 16 MB, the ESP32-S3 ROM bootloader and secondary bootloader recognize the true flash capacity without throwing `spi_flash: Detected size(16384k) larger than the size in the binary image header` warnings.

## 7. Remaining Risks and Explicit Limitations

1. **Hardware Bootloader State:** Non-destructive testing confirms the build configuration is fully aligned and ready. However, the physical ESP32-S3 hardware on `COM5` still runs its resident firmware until authorized to flash.
2. **Channel Stability:** Channel 7 is the operational channel of the TP-Link Archer C6 router in the laboratory. If router channel auto-selection or environmental DFS causes a channel shift in the future, the firmware would need to track that change. (The TP-Link router is manually fixed to Channel 7 HT20).
3. **Partition Table Unmapped Flash:** 14 MiB of the 16 MiB SPI flash remains unmapped. This is standard and completely harmless for single-partition firmware, but if advanced features like LittleFS, large NVS, or dual-bank OTA are introduced in later phases, `partitions.csv` will need to define additional partitions in that unallocated space.
4. **Physical Flashing Constraint:** Clean compilation and image validation do not guarantee RF performance under physical human interference; live signal acquisition must be audited separately once authorized.
